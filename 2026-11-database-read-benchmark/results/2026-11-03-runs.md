## Firebird 5.0.4 on Windows, local loopback without network

Client and server on the same Windows 11 VM (4 logical CPUs, Intel Core i9-9880H, Parallels on the Mac; Mac load average 3 to 8), started with `windows/local-firebird.ps1`: a copy of the installed Firebird 5.0.4 on port 53051, `fbclient.dll` 5.0.4 for FireDAC. CPU seconds are for the whole program run (connect plus three passes, 6 million rows); server CPU is what `firebird.exe` used meanwhile. "tuned" sets `RowsetSize` 10000, removes `fiMeta`, and switches on `SilentMode` and `ReadOnly`.

| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |

| FireDAC (Win64), tuned | off | 111,317 | 114,592 | 113,331 | 52.6 s | 35.2 s | 53.2 s |
| FirebirdClient (.NET 9) | off | 161,337 | 165,829 | 164,984 | 24.8 s | 36.0 s | 37.0 s |

Per row: FireDAC needs 10.6 µs of client CPU with the zoned column and 8.2 µs without, FirebirdClient 4.3 and 4.1 µs. FireDAC keeps its own core busy (client CPU equals wall time); with FirebirdClient the server is the limit (server CPU equals wall time), so about 165,000 rows per second is the ceiling of this server for one query, for every driver.

Profile of FireDAC with the zoned column (`tools/sample-windows.ps1`, 2,621 stack samples of the main thread over 15 s, build with a detailed map):

- Self time by module: `fbclient.dll` 41.5 %, the program (FireDAC, RTL, benchmark loop) 37.4 %, `ntdll.dll` 11.2 % (critical sections, fiber local storage, socket I/O), ICU 3.0 %.
- Inclusive: `isc_dsql_fetch` 44.2 % (one call per row through the legacy XSQLDA interface), `TFDPhysIBCommandBase.FetchRow` 42.1 %, of which `TIBVariable.GetData` 23.9 %; in there `TSTz2STSOff` 9.4 % (time zone conversion through ICU for every row, ICU 7.6 %) and `Int1282BCD` 7.7 % (INT128 through text, `ltoa`); DatS row list and its notifications 7.2 %, although the dataset is unidirectional.
- Names in `fbclient.dll` are the nearest exports and mean little; the time is the client library's own work between the API call and the wire.

## PostgreSQL 18.1 on Windows, local loopback without network

Same VM, started with `windows/local-postgresql.ps1`: the official EDB binaries 18.1 (zip, no installation) on port 55434, `libpq.dll` 18.1 from the same zip for FireDAC. Server CPU is not shown, the backend process ends with the connection.

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| FireDAC (Win64) | on | 180,712 | 173,104 | 166,634 | 27.2 s | 35.0 s |
| FireDAC (Win64), tuned | on | 166,392 | 170,774 | 170,489 | 28.4 s | 35.6 s |
| Npgsql (.NET 9) | on | 513,501 | 571,769 | 574,946 | 6.7 s | 11.4 s |

Per row: FireDAC 4.5 µs of client CPU, Npgsql 1.1 µs. FireDAC also waits about 8 s per program run for the server: with `fmOnDemand` and the default `CursorKind` it reads through a server cursor (`DECLARE ... CURSOR`, then `FETCH FORWARD <RowsetSize>`), so server and client take turns instead of working at the same time.

Profile of FireDAC (2,818 samples over 15 s): the program 75.9 %, `ntdll.dll` 20.6 % (11.3 % waiting in `NtWaitForSingleObject` for the next rowset), `libpq.dll` 1.9 %. FireDAC reads the binary format. Storing every row in its DatS row cache with notifications and freeing it again for the next rowset takes about 15 %, the BCD sums of the benchmark loop about 7 %.

Experiment, not part of the published program: "tuned" plus `FetchOptions.CursorKind := ckDefault`, which makes FireDAC run the plain query and let libpq buffer the whole result instead of declaring a cursor. Two interleaved rounds on a busy machine (Mac load average about 9 to 12, every number lower than above): FireDAC 90,575 to 100,895, with `ckDefault` 95,064 to 101,692, Npgsql 268,539 to 319,932 rows per second. No measurable gain; client and server still take turns, now libpq first and FireDAC after it.

## UTF-8 decode micro benchmark (`delphi/Utf8DecodeBench.dpr`)

Six million decodes of `Grüße aus Österreich, Zeile 1234567` (38 UTF-8 bytes, 35 chars), nanoseconds per call. Run 2 is the main measurement: both platforms within the same two minutes, Mac load average about 10. Run 1 ran earlier on the busier machine (load average 20 to 37).

Conformance of the proposed fix with the RTL on 11 vectors, each with flags 0 and `MB_ERR_INVALID_CHARS` (identical in both runs):

| --- | --- | --- | --- | --- |
