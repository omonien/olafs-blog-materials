## UTF-8 decode micro benchmark (`delphi/Utf8DecodeBench.dpr`)

Six million decodes of `Grüße aus Österreich, Zeile 1234567` (38 UTF-8 bytes, 35 chars), nanoseconds per call. macOS ran on the busy machine, Windows on the VM.

| Path | macOS (OSX64) | Windows (Win64) |
| --- | ---: | ---: |
| `UnicodeFromLocaleChars(CP_UTF8)` | 3,339 | 139 |
| `Utf8ToUnicode` | 3,323 | 126 |
| `TEncoding.UTF8.GetString` | 7,929 | 235 |
| iconv, one reused converter | 2,027 | |
| Proposed fix (`RtlFix.Utf8Decode`) | 389 | 135 |

Conformance of the proposed fix with the RTL on 11 vectors, each with flags 0 and `MB_ERR_INVALID_CHARS`:

- Windows (`MultiByteToWideChar`): 19 of 22 identical. The three differences are the number of U+FFFD for an overlong three-byte form, an encoded surrogate and a value above U+10FFFF, where the fix emits one U+FFFD per maximal subpart as the Unicode standard recommends.
- macOS (iconv): 15 of 22 identical. The RTL returns nothing at all for `41 E2 82` (it drops the valid `A` as well) and for the truncated `F0 9F 98`, collapses invalid sequences into a single U+FFFD, and turns `F4 90 80 80` into `?` even with `MB_ERR_INVALID_CHARS`, where Windows and the fix return 0.
